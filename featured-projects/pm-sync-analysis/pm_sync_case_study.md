# Case Study: PM Sync Failure Analysis

**Role:** Senior Technical Support Engineer, Entrata
**Timeline:** Summer 2025
**Scope:** Self-initiated analysis; 200,000+ failure records across 6 property management platforms

---

## Situation

At Entrata, property management sync pipelines run continuously — pushing lease data, resident records, and financial transactions between Entrata's platform and 6 third-party systems: Yardi, RealPage, AppFolio, ResMan, MRI, and Entrata's own PMS. These pipelines process thousands of jobs daily, and failures are inevitable at scale.

The problem wasn't the failures themselves, it was that the team had no systematic way to understand them. Every failure was treated as a unique event. Engineers triaged tickets one by one. Customer Success Managers escalated individual client complaints. There was no visibility into whether certain platforms failed more than others, which job types were most error-prone, or whether things were getting better or worse over time. The team was stuck in reactive firefighting mode.

I saw an opportunity to bring clarity to the chaos.

---

## Task

I decided to take initiative and independently scope and execute a comprehensive failure analysis. The goal was to move the team from reactive problem-solving to proactive, data-driven prioritization, and to produce something actionable that engineering leadership could actually use.

No one assigned this to me. I identified the need, built the solution, and presented the findings.

---

## Action

### Phase 1: Data Collection
I built a Python script to hit the internal RentDynamics API and extract failure records one day at a time over a 90-day window (May–August 2025). Each day's results were saved as a Parquet file for efficient downstream processing. In total I collected **200,000+ failure records** across 91 API calls.

### Phase 2: Data Organization
The raw data came back with community IDs but no context about which platform or client each community belonged to. I built a lookup table from a separate CSV mapping community IDs to their PMS system and client, then used it to split all failure records into 6 platform-specific DataFrames — one per PMS. Each row was enriched with its client ID before being saved to processed Parquet files.

### Phase 3: Error Categorization
This was the hardest part. Error messages in the raw data were completely unstructured — thousands of unique strings generated by 6 different third-party APIs with no standardization whatsoever. 

I built a **per-platform keyword matching categorization system** in Python. For each platform, I analyzed the failure messages and defined a priority-ordered set of categories with corresponding keyword lists:

- **Timeout Errors** — `timeout`, `timed out`, `response ended prematurely`
- **Authorization/Permission Errors** — `unauthorized`, `does not have permission`, `login failed`
- **Missing Object / Doesn't Exist** — `not found`, `does not exist`, `no records found`
- **HTTP / Gateway Errors** — `503`, `502`, `500`, `gateway`
- **Integration / Connection Errors** — `connection could not be established`, `not configured`, `deprecated`
- **Other** — catch-all for edge cases

Each platform had its own version of this logic to account for platform-specific error message formats. Messages were classified in priority order — the first matching category wins.

### Phase 4: Visualization
I built a full suite of charts to tell the story:

- **Community distribution pie chart** — showed ~50% of communities run on Yardi, putting raw failure volume in context
- **Annual total failures vs. failure rates by PMS** — Yardi had the highest volume, but RealPage had the highest failure *rate* (~40%), a critical distinction
- **Monthly trend lines per PMS** — tracked whether failure rates were improving or worsening over time
- **Job type breakdown per PMS** — identified which specific sync job types were driving failures within each platform

---

## Result

The analysis revealed that **80% of all failures across all 6 platforms traced back to just 5 root cause categories**: timeouts, authorization issues, missing objects, HTTP/gateway errors, and integration/connection problems.

This was a significant shift in how the team could think about the problem. Instead of treating every failure as unique, engineering could now prioritize fixes based on category impact across platforms. Instead of reacting to individual client escalations, Customer Success could see platform-level patterns.

The findings from this analysis are being built into a **real-time Domo dashboard** used by the Customer Success and Data teams for ongoing monitoring — turning a one-time analysis into a permanent operational tool.
